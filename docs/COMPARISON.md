## Not run

- **Daily, weekly and monthly budgets.** Cue counts messages in a rolling period (`FrequencyCap`), not in the user's local day, and its counters live in a database. notifkit's throttle (`src/rate-limiter`) needs Redis. Neither runs without its server, so no row compares them with `dailyBudget`; the two are different rules, not two answers to one question.
- **Next eligible time under TCPA.** tcpa-quiet-hours answers it with `nextEligibleAt`. proactive-gate's `allowedWindow` check, which `usTcpa` uses, does not yet return `nextAllowedAt`, so this is a stated loss and has no row.
- **Digests and human approval.** Cue turns a stream of events into one message per window and holds risky messages for a reviewer. proactive-gate has neither: a held message is handed back to the caller, with `nextAllowedAt` when the check that held it can name the time. This is a gap, not a comparison row.
- **Delivery.** Cue and notifkit send messages over push, SMS, email and webhooks. proactive-gate decides and never sends.
- **MCP server.** Both ship one, but each is a client of its own running server, so neither can answer without it. proactive-gate's `mcp` command decides locally. There is no equivalent call to compare.

## Limits of this comparison

- Each tool is run on the cases written in bench/upstream-cases.json. Passing them says nothing about inputs not in the file.
- The correct answers come from this repository's definition of quiet hours (the local clock, `[start, end)`). A tool that defines the window differently would be judged by ours.
- Only each tool's pure policy function is run. Cue is called through `core/policy.py` and notifkit through its `isInQuietHours`; their servers are not started, so what they do around the function is not measured.
